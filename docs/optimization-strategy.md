# RFP Demo — 속도 최적화 전략 검토

> 2026-07-11 | 브랜치: feat/worker-pattern

## 현재 상태

### 파이프라인

```
PDF (76,705자)
  ↓ pdf-parse (2초)
텍스트 정제
  ↓ 정규식 스캔
59개 ID 발견
  ↓ ID 경계 블록 분할
59개 블록 (각 300~2000자)
  ↓ 블록당 LLM 호출 1회
59회 호출 → name, sourceText, type, priority 추출
  ↓
DB 저장
```

### 속도

| 모델 | 호출당 | 59회 총합 | coverage |
|------|--------|----------|----------|
| minimax-m2.7 | — | — | 0% (현재 작동 안 함) |
| kimi-k2.6 | 17초 | **~17분** | 100% |
| gpt-4o-mini (미보유) | 2초 | ~2분 | 100% |

### 병목 분석

```
전체 17분 중:
- PDF 파싱:    2초  (< 1%)
- LLM 호출:    ~16분 50초 (99%)  ← 병목
```

**59회 네트워크 왕복**이 근본 원인입니다.

---

## 최적화 전략 (80-90% coverage, 속도 우선)

### 전략 A: 그룹 호출 (단순, 효과적)

5개 ID씩 묶어서 한 번에 호출:

```
"ECR-001, ECR-002, ECR-003, ECR-004, ECR-005의
name, sourceText, type, priority를 모두 추출해줘"
```

| 항목 | 현재 | 전략 A |
|------|------|--------|
| 호출 횟수 | 59회 | 12회 |
| 예상 시간 (kimi) | 17분 | **~3.5분** |
| 예상 coverage | 100% | 80~90% |
| 코드 변경 | — | 블록 그룹화 로직 추가 |

⚠️ 일부 ID 누락 가능성 있음 (LLM이 5개 중 4개만 반환)

---

### 전략 B: LLM(구조) + Regex(원문) 분리 (권장) ⭐

LLM은 **짧은 필드만** 추출하고, `sourceText`는 정규식으로 직접 가져옵니다.

```
Phase 1 (LLM): 10~15개 ID씩 그룹 호출 → name, type, priority만 추출
               59 ID → 4~6회 호출 → ~1.5분

Phase 2 (Regex): 각 ID 블록에서 "요구사항 상세설명" / "세부내용" 이후 텍스트 추출
                 호출 0회 → 0초
```

| 항목 | 현재 | 전략 B |
|------|------|--------|
| LLM 호출 | 59회 | 4~6회 |
| Regex 추출 | 0회 | 59회 (순수 계산) |
| 예상 시간 (kimi) | 17분 | **~1.5분** |
| 예상 coverage | 100% | 85~95% |
| 코드 변경 | — | LLM 프롬프트 축소 + regex fallback |

**장점**: LLM이 추출할 필드가 절반으로 줄어 응답이 짧아짐 → 더 빠름  
**단점**: sourceText가 정규식으로 완벽히 추출되지 않을 수 있음 (RFP 형식 의존)

---

### 전략 C: 병렬 호출 (Worker 내 동시처리)

블록을 3~5개씩 병렬로 호출:

```
Promise.all([
  callLLM(block1),  // ECR-001
  callLLM(block2),  // ECR-002
  callLLM(block3),  // ECR-003
])
```

| 항목 | 현재 | 전략 C |
|------|------|--------|
| 호출 횟수 | 59회 (순차) | 59회 (5개씩 병렬) |
| 예상 시간 (kimi) | 17분 | **~3.5분** |
| coverage | 100% | 100% |

⚠️ 병렬 호출 = API rate limit 위험, DB 커넥션 풀 고려 필요

---

### 전략 D: 하이브리드 (B + C)

전략 B(그룹+regex)와 C(병렬)를 결합:

```
Phase 1: 4~6회 그룹 호출 (name/type/priority) → 병렬 2개씩 → ~1분
Phase 2: Regex sourceText 추출 → 0초
```

예상: **~1분**, coverage 85~95%
