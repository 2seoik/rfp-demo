이전 단계에서 RFP 요구사항의 `sourceText`를 ID 경계 블록 원문으로 직접 저장하고, LLM은 name, type, priority 등 의미 필드만 반환하도록 변경했습니다.

이제 LLM 호출을 배치화하고 제한된 병렬 처리를 적용해 주세요.

## **현재 문제**

현재 요구사항이 59개이면 LLM 호출도 59회 발생합니다.

각 호출이 약 17초이므로 전체 처리 시간이 약 17분입니다.

목표 구조는 다음과 같습니다.

```text
59개 요구사항
→ 토큰 또는 문자 길이를 기준으로 6~10개 배치 생성
→ 배치 단위 LLM 호출
→ 동시 실행 수 2
→ 응답 ID 검증
→ 누락·오류 ID만 소규모 재시도
```

## **목표**

- 최초 LLM 호출 수를 약 6~10회로 감소
- ID coverage 100% 유지
- 누락 ID만 재시도
- API rate limit을 피하기 위해 제한된 동시성 적용
- 한 배치 실패가 전체 문서 실패로 이어지지 않도록 처리
- 기존 Worker와 DB 구조를 최대한 유지

## **필수 변경사항**

### **1. 배치 생성 함수 구현**

요구사항 배열을 LLM 요청용 배치로 분리하는 함수를 작성하세요.

단순히 개수만 기준으로 나누지 말고 다음 두 조건을 함께 적용하세요.

```ts
maxItemsPerBatch = 10;
maxCharactersPerBatch = 16000;
```

다음 조건 중 먼저 도달하는 시점에 배치를 종료하세요.

- 배치에 요구사항이 10개 포함됨
- 요구사항 sourceText 합계가 약 16,000자를 초과하려 함

하나의 블록이 최대 문자 수를 초과하더라도 그 블록 하나만 별도 배치로 처리하세요.

설정값은 환경변수 또는 설정 상수로 쉽게 조정할 수 있어야 합니다.

권장 환경변수:

```env
RFP_LLM_BATCH_MAX_ITEMS=10
RFP_LLM_BATCH_MAX_CHARS=16000
RFP_LLM_CONCURRENCY=2
RFP_LLM_MAX_RETRIES=2
RFP_LLM_TIMEOUT_MS=60000
```

환경변수가 없으면 안전한 기본값을 사용하세요.

### **2. 배치 LLM 요청 스키마**

LLM에 다음과 유사한 구조로 전달하세요.

```json
{
  "requirements": [
    {
      "id": "ECR-001",
      "text": "원문 블록"
    },
    {
      "id": "ECR-002",
      "text": "원문 블록"
    }
  ]
}
```

LLM 출력은 반드시 다음 형태여야 합니다.

```json
{
  "requirements": [
    {
      "id": "ECR-001",
      "name": "요구사항 명칭",
      "type": "SYSTEM_COMMON",
      "priority": "HIGH"
    }
  ]
}
```

sourceText는 출력에 포함하지 마세요.

### **3. 프롬프트 계약 강화**

시스템 또는 사용자 프롬프트에 다음 규칙을 명확히 작성하세요.

```text
입력으로 받은 모든 ID에 대해 정확히 하나의 결과를 반환한다.
ID 문자열을 수정하지 않는다.
입력에 없는 ID를 생성하지 않는다.
같은 ID를 두 번 반환하지 않는다.
결과는 입력 순서를 유지한다.
판단할 수 없는 값은 null로 반환한다.
JSON 외의 설명이나 마크다운을 출력하지 않는다.
```

LLM 출력의 예시도 프롬프트에 포함하세요.

### **4. ID reconciliation 구현**

각 배치 응답에 대해 다음을 검사하는 함수를 구현하세요.

- 입력 ID 목록
- 출력 ID 목록
- 누락된 ID
- 중복된 ID
- 입력에 존재하지 않는 ID
- 빈 name
- 허용되지 않은 type
- 허용되지 않은 priority
- JSON 파싱 실패
- 결과 배열 누락

예상 함수 형태:

```ts
type ReconciliationResult = {
  valid: EnrichedRequirement[];
  missingIds: string[];
  duplicateIds: string[];
  unknownIds: string[];
  invalidIds: string[];
};
```

LLM 출력 순서를 신뢰하지 말고 ID를 기준으로 원본 요구사항과 결합하세요.

### **5. 실패 ID만 재시도**

배치에 10개가 들어 있고 2개가 누락되었다면 10개 전체를 다시 호출하지 마세요.

누락되거나 유효하지 않은 2개만 다시 요청하세요.

재시도는 다음 순서로 처리하세요.

```text
1차: 일반 배치 요청
2차: 누락·오류 ID만 작은 배치로 요청
3차: 그래도 실패한 ID는 개별 요청
최종 실패: DB에 FAILED 또는 PARTIAL 상태 기록
```

재시도 횟수는 설정값으로 관리하세요.

같은 오류에 무한 재시도하지 마세요.

### **6. 제한된 병렬 처리**

모든 배치를 한 번에 `Promise.all()`로 실행하지 마세요.

동시 실행 수를 제한하는 큐 또는 concurrency limiter를 구현하세요.

기존 프로젝트에 `p-limit`이 있으면 사용하고, 없다면 불필요한 패키지를 추가하지 않고 간단한 Worker pool을 구현해도 됩니다.

초기 기본 동시성은 2로 설정하세요.

```ts
const concurrency = 2;
```

각 배치 실행은 독립적으로 성공 또는 실패할 수 있어야 합니다.

`Promise.allSettled()` 또는 동등한 구조를 사용하여 하나의 배치 실패가 다른 배치 결과를 취소하지 않도록 하세요.

### **7. timeout과 오류 분류**

LLM 요청에 timeout을 적용하세요.

다음 오류를 구분해 로깅하세요.

- timeout
- HTTP 429
- HTTP 5xx
- JSON parse error
- schema validation error
- empty response
- ID mismatch
- unknown error

429와 5xx에는 지수 백오프를 적용하세요.

예:

```text
1차 재시도: 약 1초
2차 재시도: 약 2초
3차 재시도: 약 4초
```

고정값 대신 약간의 jitter를 추가해도 됩니다.

스키마 오류나 ID 불일치는 네트워크 재시도와 별도로 실패 ID 재요청 대상으로 처리하세요.

### **8. 부분 성공 저장**

각 요구사항은 독립적으로 상태를 가질 수 있어야 합니다.

기존 스키마에 상태 필드가 있다면 활용하고, 없다면 최소 변경으로 다음 상태를 표현하세요.

```text
PENDING
PROCESSING
COMPLETED
FAILED
```

문서 전체 상태도 다음과 같이 구분하는 것이 좋습니다.

```text
PROCESSING
COMPLETED
PARTIAL
FAILED
```

59개 중 58개가 성공하고 1개가 실패한 경우 전체를 FAILED로 만들지 말고 PARTIAL로 처리하세요.

DB 스키마를 크게 바꾸기 어렵다면 기존 status 또는 error 컬럼을 활용하세요.

### **9. 진행률 계산**

프론트 또는 API에서 진행률을 표시할 수 있도록 가능한 경우 다음 값을 업데이트하세요.

```ts
{
  totalRequirements: 59,
  completedRequirements: 35,
  failedRequirements: 1,
  progressPercent: 61
}
```

기존 진행률 구조가 있다면 그것을 재사용하세요.

2초 polling 구조에서 진행 상황을 확인할 수 있어야 합니다.

### **10. 로그 개선**

배치마다 다음 정보를 구조화해 기록하세요.

```text
documentId
batchIndex
batchSize
inputIds
attempt
model
elapsedMs
resultCount
missingIds
invalidIds
errorType
```

원문 전체나 개인정보가 로그에 과도하게 기록되지 않도록 하세요.
