현재 프로젝트의 RFP 요구사항 추출 Worker를 분석하고 아래 요구사항대로 수정해 주세요.

## **프로젝트 개요**
#### **`source-text-refactor.md`**

사용자가 RFP PDF를 업로드하면 Worker가 다음 순서로 처리합니다.

1. pdf-parse로 PDF 텍스트 추출
2. 정규식 `/[A-Z]{2,4}-\d{3}/g`로 요구사항 ID 검출
3. 각 ID 위치를 기준으로 59개 요구사항 블록 분할
4. 각 블록을 LLM에 개별 요청
5. LLM이 id, name, sourceText, type, priority 반환
6. 응답 검증 후 PostgreSQL에 저장

현재 테스트 PDF는 약 76,705자이며 요구사항 ID는 59개입니다.

현재 가장 큰 문제는 59개의 요구사항마다 LLM을 한 번씩 호출하여 약 17분이 걸린다는 것입니다.

## **이번 단계의 목표**

LLM이 `sourceText`를 생성하거나 추출하지 않도록 구조를 변경하세요.

이미 ID 경계로 요구사항 블록이 만들어지므로 해당 블록 원문 자체를 `sourceText`로 저장해야 합니다.

## **필수 변경사항**

### **1. 요구사항 블록 생성 구조 확인**

현재 코드에서 다음 로직을 찾아주세요.

- PDF 텍스트에서 요구사항 ID 위치를 검출하는 코드
- 현재 ID부터 다음 ID 직전까지 블록을 분할하는 코드
- 각 블록을 LLM으로 전달하는 코드
- LLM 응답을 DB에 저장하는 코드

프로젝트 구조와 관련 파일을 먼저 확인한 후 변경하세요.

### **2. sourceText를 코드에서 직접 설정**

각 요구사항 객체는 LLM 호출 전에 다음 데이터를 가져야 합니다.

```ts
{
  id: "ECR-001",
  sourceText: "현재 ID부터 다음 ID 직전까지의 원문 블록",
  name: null,
  type: null,
  priority: null
}
```

LLM 응답에서 `sourceText`를 받지 마세요.

LLM이 반환한 `sourceText`가 기존 코드에 존재한다면 무시하거나 응답 스키마에서 제거하세요.

### **3. 원본과 정규화 텍스트 분리 검토**

DB 스키마 변경이 과도하지 않다면 다음 구조를 적용하세요.

```ts
{
  sourceTextRaw: "PDF에서 추출된 원본 블록",
  sourceText: "공백, 페이지 헤더, 푸터 등을 정리한 표시용 텍스트"
}
```

기존 DB 호환성 문제로 컬럼 추가가 어렵다면 현재 `sourceText` 컬럼에 원본 블록을 저장하세요.

불필요한 DB 마이그레이션은 만들지 마세요.

### **4. LLM 요청 필드 축소**

LLM에는 다음 필드만 요청하세요.

```ts
{
  id: string;
  name: string;
  type: string | null;
  priority: string | null;
}
```

프롬프트에서 다음 내용을 제거하세요.

- sourceText 생성 요청
- 원문 전체를 다시 작성하라는 요청
- sourceText 요약 또는 정제 요청

LLM이 판단할 수 없는 값은 임의 생성하지 말고 `null`을 반환하도록 프롬프트를 수정하세요.

### **5. ID 접두어 기반 type 처리 검토**

프로젝트에서 ID 접두어가 유형을 명확하게 의미하는지 확인하세요.

예:

```ts
const REQUIREMENT_TYPE_BY_PREFIX = {
  ECR: "시스템 공통 요구사항",
  SFR: "기능 요구사항",
  SER: "보안 요구사항",
};
```

기존 코드나 RFP 문서에 명확한 매핑이 있을 때만 규칙 기반으로 처리하세요.

매핑이 명확하지 않은 접두어는 LLM이 판단하거나 `null`로 남기세요.

매핑을 코드 여러 곳에 하드코딩하지 말고 하나의 설정 객체나 함수로 관리하세요.

### **6. LLM 실패 시에도 기본 데이터 저장**

LLM 호출이 실패하더라도 다음 정보는 유지되어야 합니다.

- 요구사항 ID
- sourceText
- 문서 내 순서
- 원문 위치 또는 블록 인덱스
- 가능한 경우 규칙 기반 type

LLM 장애 때문에 전체 요구사항 결과가 0건이 되지 않도록 수정하세요.

가능하다면 요구사항 기본 행을 먼저 생성하고 LLM 결과로 보강하는 구조를 사용하세요.

### **7. 응답 스키마와 타입 수정**

다음 항목을 모두 확인하세요.

- TypeScript 인터페이스
- Zod 스키마 또는 JSON Schema
- LLM 응답 파서
- DB insert/update 코드
- API 응답 타입
- 프론트엔드 타입
- 테스트 mock 데이터

`sourceText`가 LLM 응답에 필수인 구조가 남아 있지 않도록 전체 코드에서 검색하세요.

## **테스트 요구사항**

다음 테스트를 추가하거나 수정하세요.

1. ID 경계 블록이 `sourceText`로 저장되는 테스트
2. LLM 응답에 sourceText가 없어도 정상 처리되는 테스트
3. LLM 호출 실패 시 ID와 sourceText가 유지되는 테스트
4. 다음 ID 직전까지만 블록에 포함되는 테스트
5. 마지막 ID는 문서 끝까지 포함되는 테스트
6. 기존 테스트 전체 통과

현재 vitest 테스트가 약 22개 있으므로 기존 테스트를 깨뜨리지 마세요.
