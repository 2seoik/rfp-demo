`AGENTS.md`와 다음 문서를 먼저 읽으십시오.

- `docs/agent/rfp-pipeline-spec.md`
- `docs/agent/STATUS.md`
- `docs/agent/report/` 아래의 관련 보고서가 존재하면 해당 문서

이번 세션은 **독립적인 읽기 전용 변경 검토**입니다.

선택적으로 지정된 검토 초점은 다음과 같습니다.

```text
${ARGUMENTS:-전체 변경사항}
````

검토 초점이 비어 있으면 현재 working tree의 전체 변경사항을 검토하십시오.

## **절대 규칙**

이번 세션에서는 소스 코드, 테스트, 설정, 문서, migration 또는 Git 상태를 수정하지 마십시오.

다음 행위를 하지 마십시오.

- 파일 생성, 수정 또는 삭제
- 자동 수정 옵션이 포함된 lint 실행
- formatter 실행
- 패키지 설치 또는 업데이트
- migration 생성 또는 적용
- DB 데이터 변경
- `git add`
- `git commit`
- `git push`
- `git reset`
- `git clean`
- `git rebase`
- 문제를 직접 수정
- 실제 비밀정보 출력

문제가 발견되면 수정하지 말고 정확한 위치와 수정 방향만 보고하십시오.

## **검토 대상 확인**

먼저 다음을 확인하십시오.

```bash
git status --short
git diff --stat
git diff
git diff --cached
```

현재 변경이 없다면 이를 명확히 보고하고 중단하십시오.

추적되지 않은 파일이 있다면 내용 확인이 필요한 파일과 확인하면 안 되는 민감 파일을 구분하십시오.

다음 파일의 실제 값은 출력하지 마십시오.

- `.env`
- 인증서
- 키 파일
- credential 파일
- 업로드된 내부 문서
- 로그에 포함된 민감정보

## **검토 기준**

### **1. 작업 범위 준수**

다음을 확인하십시오.

- 지정된 단계만 구현했는지
- 다음 단계까지 미리 구현하지 않았는지
- 무관한 리팩터링이 포함되었는지
- UI나 API에 불필요한 변경이 있는지
- 기존 공개 API 필드가 삭제 또는 변경되었는지
- 생성 파일이나 개인 환경 파일이 포함되었는지

### **2. 실제 원인 해결 여부**

변경이 증상만 완화하는지 실제 원인을 해결하는지 확인하십시오.

특히 다음 우회 처리가 없는지 확인하십시오.

- `max_tokens`만 증가
- 문자 청크 크기만 변경
- overlap만 증가
- 20,000자 제한을 유지하면서 모델만 변경
- 실패를 로그로만 남기고 정상 완료
- 기대 결과를 현재 출력에 맞춰 낮춤
- 오류를 `any` 또는 타입 단언으로 숨김

### **3. 전체 문서 ID 검출**

관련 변경이 있다면 다음을 확인하십시오.

- 전체 문서에서 ID를 검색하는지
- ID 정규화가 일관적인지
- `SFR-1`, `SFR 001`, `SFR_001`, `SFR–001` 등이 동일 ID로 처리되는지
- 알려진 prefix 외 신규 prefix를 무조건 제거하지 않는지
- 날짜, 버전, 페이지 번호 오탐을 적절히 제한하는지
- 정규식의 `lastIndex` 재사용 버그가 없는지
- offset이 원문 기준으로 정확한지
- 중복 후보가 손실 없이 수집되는지

### **4. 요구사항 경계 분할**

관련 변경이 있다면 다음을 확인하십시오.

- 현재 ID부터 다음 ID 직전까지가 기본 후보인지
- 마지막 ID가 문서 끝까지 포함되는지
- 첫 번째 ID 이전 텍스트를 잘못 요구사항으로 포함하지 않는지
- ID가 같은 줄이나 표 셀에서 반복될 때 동작이 안전한지
- 한 요구사항이 긴 경우 다른 요구사항과 섞이지 않는지
- UTF-16 JavaScript offset과 저장 offset의 의미가 일관적인지
- 너무 짧은 후보와 목차 후보를 구분하는지

### **5. 동일 ID 중복 후보 선택**

관련 변경이 있다면 다음을 확인하십시오.

- 첫 번째 또는 마지막 후보만 선택하지 않는지
- 총괄표보다 상세 블록을 선호하는지
- 품질 점수 규칙이 결정론적인지
- 동일 점수일 때 tie-break 규칙이 있는지
- 선택되지 않은 출처도 필요 시 보존하는지
- 반복 헤더나 페이지 번호가 점수를 왜곡하지 않는지

### **6. 원문 보존**

다음을 확인하십시오.

- `rawSourceText`가 파서 원문인지
- LLM 출력이 raw source를 덮어쓰지 않는지
- normalized description과 raw source가 분리되는지
- offset 또는 page 정보가 선택된 원문과 일치하는지
- LLM 실패 시에도 원문 저장이 가능한지

### **7. LLM 호출과 검증**

관련 변경이 있다면 다음을 확인하십시오.

- 입력 ID를 LLM이 변경할 수 없게 했는지
- 모든 입력 후보가 출력에 존재하는지 검증하는지
- 배열 여부와 JSON 파싱을 검사하는지
- 알 수 없는 ID 생성 여부를 검사하는지
- 중복 ID를 검사하는지
- type과 priority enum을 검사하는지
- 일부 누락 시 누락 후보만 재시도하는지
- 전체 문서를 불필요하게 재전송하지 않는지
- timeout과 provider error를 구분하는지
- 실패 시 `raw_only`가 보존되는지
- 모든 호출 실패를 정상 완료로 처리하지 않는지

### **8. DB 일관성과 멱등성**

관련 변경이 있다면 다음을 확인하십시오.

- requirements와 responses가 하나의 transaction에 있는지
- transaction callback 안팎의 DB client가 혼용되지 않는지
- job 완료 처리가 commit 전에 노출되지 않는지
- 중간 실패 시 partial data가 남는지
- 재시도 시 이전 결과와 새 결과가 섞이는지
- unique constraint가 실제 재시도 단위와 맞는지
- upsert가 다른 분석 실행의 데이터를 잘못 덮어쓰는지
- 프로젝트 삭제 시 새 FK가 삭제를 막지 않는지
- migration 순서가 nullable 추가 → backfill → 코드 전환 → constraint 강화인지
- 기존 데이터에 즉시 NOT NULL을 적용하지 않는지

### **9. Worker 동시성과 복구**

관련 변경이 있다면 다음을 확인하십시오.

- `FOR UPDATE SKIP LOCKED`가 transaction 안에서 사용되는지
- job claim과 status 변경 사이 race condition이 없는지
- 모든 processing job을 무조건 복구하지 않는지
- stale 기준이 명확한지
- 최신 processing job을 건드리지 않는지
- 두 Worker가 동일 프로젝트를 동시에 분석할 가능성
- retry attempt와 무한 재시도 가능성
- heartbeat 또는 updated_at 갱신 방식
- Worker 종료 후 일관성

### **10. 상태 및 메트릭**

다음을 확인하십시오.

- 발견 ID 수와 최종 저장 ID 수 차이가 기록되는지
- coverage ratio의 분모가 올바른지
- 중복 수 계산이 정확한지
- `rawOnlyCount`, `failedCount`, `llmEnrichedCount`가 중복 계산되지 않는지
- 일부 성공을 완전 성공으로 표시하지 않는지
- 0건 결과를 정상 완료하지 않는지
- 기존 UI가 기대하는 상태값을 깨뜨리지 않는지
- jobs.result 또는 message 크기가 과도하지 않은지

### **11. 보안**

다음을 확인하십시오.

- API 키 하드코딩
- `.env` 추적
- 로그의 Authorization header
- DB URL 출력
- LLM request header 출력
- 원문 전체를 디버그 로그에 출력
- 오류 객체에 credential이 포함될 가능성
- `.env.example`의 실제 값
- migration 또는 fixture에 실제 내부 데이터 포함

실제 값을 보고서에 복사하지 말고 `[REDACTED]`로 표시하십시오.

### **12. 테스트 품질**

다음을 확인하십시오.

- 성공 경로만 테스트하지 않는지
- 문서 마지막 ID 테스트
- 중복 ID 테스트
- 목차와 상세표 중복 테스트
- 신규 prefix 테스트
- 오탐 테스트
- LLM 일부 누락 테스트
- LLM 전체 실패 테스트
- Worker 재시도 테스트
- transaction rollback 테스트
- 프로젝트 삭제 테스트
- 기존 API 응답 호환 테스트
- golden dataset을 실제 출력에 맞춰 변경하지 않았는지

테스트 코드가 운영 로직을 그대로 복제하여 동일한 버그를 공유하지 않는지도 확인하십시오.

## **검증 명령**

먼저 `package.json`에서 실제 script를 확인하십시오.

소스 코드를 수정하지 않는 명령만 실행할 수 있습니다.

예:

```bash
pnpm typecheck
pnpm test
pnpm build
```

다음 조건을 지키십시오.

- 존재하지 않는 script를 실행하지 않음
- `--fix`, `--write`, update snapshot 옵션 사용 금지
- 외부 LLM 또는 DB가 필요한 테스트는 환경이 명확한 경우에만 실행
- 명령 실행 전후 `git status --short`를 비교
- 검증 과정에서 추적 파일이 변경되면 즉시 보고하고 더 진행하지 않음

검증 명령 실행이 위험하거나 매우 오래 걸릴 것으로 판단되면 실행하지 말고 권장 명령으로만 보고하십시오.

## **심각도 기준**

발견 사항을 다음 기준으로 분류하십시오.

### **Critical**

- 데이터 손실
- 비밀정보 노출
- 운영 DB 파괴 가능성
- 동일 job의 동시 처리로 심각한 데이터 불일치
- 기존 업로드 또는 프로젝트 조회 완전 중단

### **High**

- 요구사항 대량 누락
- 중복 저장
- transaction 불일치
- 모든 LLM 실패를 정상 완료
- 재시도 후 이전 결과와 새 결과 혼합
- 프로젝트 삭제 실패
- migration 적용 시 기존 데이터 손상

### **Medium**

- 일부 edge case 누락
- 메트릭 부정확
- 상태 표시 부정확
- 부족한 오류 처리
- 테스트 공백
- 성능 악화 가능성

### **Low**

- 명명, 문서, 유지보수성
- 비핵심 로그 개선
- 사소한 중복 코드

### **9. 선택적 개선**

어떤 파일도 수정하지 말고 검토 보고 후 중단하십시오.

````

````

```md
$ARGUMENTS
```

그리고 바로 아래에 다음 문장을 추가하십시오.
