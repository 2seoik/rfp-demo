`AGENTS.md`와 다음 문서를 먼저 읽으십시오.

- `docs/agent/rfp-pipeline-spec.md`
- `docs/agent/STATUS.md`
- `docs/project-summary.md`가 존재하면 해당 문서
- `docs/agent/report/` 아래의 관련 진단 보고서가 존재하면 해당 문서

이번 세션에서 수행할 작업 범위는 다음과 같습니다.

```text
$ARGUMENTS
````

`$ARGUMENTS`가 비어 있으면 작업 범위를 추정하지 마십시오.

다음 사용 예시를 안내하고 즉시 중단하십시오.

```text
/rfp-phase "M1-A: 기존 동작을 변경하지 않고 진단 로그와 계측만 추가"
/rfp-phase "M1-B: 전체 문서 요구사항 ID 검출과 정규화 구현"
/rfp-phase "M1-C: ID 경계 후보 분할과 중복 후보 품질 선택 구현"
/rfp-phase "M2: LLM 보강 응답 검증과 raw_only 보존 구현"
/rfp-phase "M3: 분석 결과 저장 트랜잭션과 중복 방지 구현"
```

## **핵심 원칙**

1. 이번 세션에서는 지정된 단계 하나만 수행합니다.
2. 다음 단계의 코드를 미리 구현하지 마십시오.
3. 실제 코드를 먼저 확인하고 문서의 설명과 다르면 실제 구현을 기준으로 판단하십시오.
4. 기존 코드를 전면 재작성하지 마십시오.
5. 기존 업로드, 프로젝트 조회, 진행률, 삭제, polling, 유사 검색 기능을 보존하십시오.
6. 기존 API 응답 필드를 제거하거나 이름을 바꾸지 마십시오.
7. 필요한 경우 기존 필드를 유지하면서 새 필드를 추가하십시오.
8. 애플리케이션에서 사용하는 `deepseek-v4-flash` 모델은 이번 단계가 명시적으로 모델 변경을 요구하지 않는 한 변경하지 마십시오.
9. LLM이 반환한 값으로 파서 원문을 덮어쓰지 마십시오.
10. 테스트하지 않은 내용을 완료했다고 보고하지 마십시오.

## **금지 사항**

사용자의 별도 명시적 지시 없이 다음 행위를 하지 마십시오.

- `git commit`
- `git push`
- `git reset`
- `git clean`
- `git rebase`
- 운영 DB migration 적용
- `drizzle push` 또는 이에 준하는 직접 schema 변경
- `TRUNCATE`, `DROP`, 무제한 `DELETE`
- 실제 API 키, 토큰, 비밀번호, DATABASE_URL 출력
- 전체 프로젝트 아키텍처 재작성
- 무관한 UI 재디자인
- 대규모 의존성 교체
- 원인 확인 없는 PDF 파서 교체
- 단순 `max_tokens` 증가만으로 문제 해결 처리
- TypeScript 오류를 불필요한 `any`로 숨김
- golden dataset의 기대값을 실제 실패 결과에 맞춰 낮춤
- 존재하지 않는 테스트 명령 실행을 성공했다고 보고

## **작업 순서**

### **1. 현재 상태 확인**

먼저 다음을 확인하십시오.

- 현재 branch
- working tree 상태
- 기존 미커밋 변경
- 이번 단계와 관련된 실제 파일
- `docs/agent/STATUS.md`의 이전 단계 결과

기존 사용자 변경을 덮어쓰거나 되돌리지 마십시오.

### **2. 실제 구현 조사**

이번 단계와 관련된 호출 경로를 추적하십시오.

다음을 문서 설명만으로 가정하지 마십시오.

- 파일 존재 여부
- 함수명
- DB 테이블 및 컬럼
- API 응답 형식
- package.json script
- 테스트 프레임워크
- migration 방식

### **3. 원인과 완료 조건 정의**

코드를 수정하기 전에 내부적으로 다음을 명확히 하십시오.

- 이번 단계에서 해결할 실제 문제
- 변경하지 않을 범위
- 수정할 파일
- 예상되는 기존 기능 영향
- 단계 완료 조건
- 검증 방법

예상보다 넓은 schema 변경이나 대규모 리팩터링이 필요하면 코드를 수정하지 말고 다음을 보고한 뒤 중단하십시오.

- 필요한 추가 변경
- 예상 수정 파일
- 기존 기능에 대한 위험
- 더 작은 대안
- 사용자 결정이 필요한 항목

### **4. 최소 범위 구현**

지정된 단계에 필요한 최소 변경만 수행하십시오.

구현 시 다음 원칙을 따르십시오.

- 기존 공용 함수와 API 형식을 가능한 한 유지
- 새 로직은 독립적으로 테스트 가능하게 작성
- 결정론적 처리와 LLM 처리를 분리
- 원문과 정규화 결과를 분리
- 실패 시 기존에 검출된 원문을 보존
- 재시도 가능성을 고려
- 중복 저장을 방지
- 오류를 조용히 삼키지 않음
- 로그에 비밀정보를 포함하지 않음

### **5. 테스트 작성**

이번 단계의 동작을 검증하는 테스트를 작성하거나 갱신하십시오.

테스트 원칙:

- 운영 코드를 테스트 안에 복제하지 않음
- 실제 parser 테스트와 LLM 호출 테스트를 분리
- LLM 없이 검증 가능한 로직은 순수 unit test로 작성
- 기존 테스트 문서가 없으면 결과를 임의로 만들지 않음
- golden dataset이 없으면 필요한 형식을 제안하되 정답을 추정하지 않음
- 테스트 fixture에 비밀정보나 내부 문서를 새로 커밋하지 않음

### **6. 검증 명령 확인 및 실행**

먼저 `package.json`을 확인한 뒤 실제 존재하는 script만 실행하십시오.

가능한 검증 예시:

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

script가 없으면 실행하지 말고 `존재하지 않음`으로 보고하십시오.

검증 결과는 다음과 같이 구분하십시오.

- 이번 변경 검증 성공
- 이번 변경으로 인한 실패
- 기존부터 존재한 실패
- 환경 또는 외부 서비스 문제
- 테스트 데이터 부족으로 검증 불가

DB나 외부 LLM이 필요한 테스트는 테스트 환경이 명확하게 준비된 경우에만 실행하십시오.

### **7. Diff 검토**

수정 후 다음을 확인하십시오.

- 지정된 단계 밖의 파일이 수정되지 않았는지
- 비밀정보가 diff에 포함되지 않았는지
- 디버깅용 임시 코드가 남지 않았는지
- API 기존 필드가 제거되지 않았는지
- 무관한 formatting 변경이 과도하지 않은지
- migration이 기존 데이터를 파괴하지 않는지
- 테스트 결과를 실제보다 과장하지 않았는지

### **8. STATUS 갱신**

`docs/agent/STATUS.md`가 존재하면 실제로 확인한 사실만 기록하십시오.

다음을 포함하십시오.

- 수행 단계
- 날짜
- 변경 파일
- 실행 명령
- 테스트 결과
- 검증 불가 항목
- 남은 위험
- 권장 다음 단계

기존 기록을 삭제하지 말고 필요한 경우 새 섹션을 추가하십시오.

민감한 값은 기록하지 마십시오.

## **단계별 추가 원칙**

### **진단 또는 계측 단계인 경우**

- 핵심 동작을 바꾸지 마십시오.
- 전체 텍스트 길이, ID 개수, offset 범위, prefix 통계 등을 구조화된 로그로 추가하십시오.
- API 키나 원문 전체를 로그로 출력하지 마십시오.

### **ID 검출 단계인 경우**

- 전체 문서에서 ID를 탐색하십시오.
- ID 정규화와 후보 탐색을 분리하십시오.
- 알려진 prefix만으로 새로운 prefix를 모두 제거하지 마십시오.
- 날짜, 버전, 페이지 번호 오탐에 대한 테스트를 포함하십시오.

### **요구사항 경계 분할 단계인 경우**

- 현재 ID부터 다음 ID 직전까지를 기본 후보로 사용하십시오.
- 하나의 요구사항이 긴 경우 해당 요구사항 내부에서만 보조 청킹하십시오.
- 동일 ID의 모든 후보를 수집한 뒤 품질 점수로 대표 후보를 선택하십시오.
- 첫 번째 또는 마지막 후보만 무조건 선택하지 마십시오.

### **LLM 보강 단계인 경우**

- 시스템이 검출한 ID를 LLM이 수정하지 못하게 하십시오.
- 모든 입력 후보에 정확히 하나의 결과가 있어야 합니다.
- 입력 ID와 출력 ID를 검증하십시오.
- 누락된 후보만 재시도하십시오.
- 실패 후보는 `raw_only`로 보존하십시오.
- LLM 응답으로 raw source를 덮어쓰지 마십시오.

### **DB 저장 단계인 경우**

- requirements와 responses 저장을 하나의 transaction으로 묶으십시오.
- 동일 분석 실행의 재시도 시 결과가 섞이지 않게 하십시오.
- unique constraint 또는 upsert 전략을 검토하십시오.
- migration은 생성 및 검토까지만 수행하고 실제 DB 적용은 별도 지시를 기다리십시오.

### **Worker 복구 단계인 경우**

- 모든 processing job을 무조건 pending으로 돌리지 마십시오.
- stale job만 복구하십시오.
- 복구 기준 시간을 상수 또는 환경변수로 관리하십시오.
- 복구 사실과 attempt를 기록하십시오.
